# Спека: тонкий CLI поверх ядра

**Статус:** спека на реализацию. **Дата:** 2026-08-09. **Автор:** роль `spec-owner`.
**Норматив формата** — [`handoff-v2-contract.md`](handoff-v2-contract.md); при любом расхождении
прав он, а не этот документ.

## 1. Зачем

Сегодня ядро доступно только через pi: команды `session-link*` регистрируются в
[`src/index.ts`](../src/index.ts), и он же единственный тянет зависимости pi. Всё остальное —
`store`, `handoff`, `parent`, `doctor`, `graph`, `types` (~2200 строк) — **от pi не зависит вовсе**.

CLI открывает это ядро всем остальным: Claude Code, Hermes, скриптам, диспетчеру флота.

**Что это даёт, чего «общий формат» не даст никогда:** один store, один индекс, один лок, одни
id — значит линия работы, начатая в pi, продолжается в Claude Code и наоборот. Сейчас это
невозможно в принципе. Второй довод проверен практикой: парная спека для Claude Code разошлась
с контрактом за неделю **без единой строчки кода**. Второй реализации формата быть не должно.

**Стоимость нулевая, и это проверено:** у пакета **ноль рантайм-зависимостей** (peer — только
`@earendil-works/pi-coding-agent` и `typebox`, оба нужны исключительно pi-адаптеру), `type: module`,
`engines.node >= 22.19`, сборки нет — тесты уже гоняются как
`node --test --experimental-strip-types`. CLI запускается тем же способом и не требует ни
установки, ни компиляции.

## 2. Границы: чем CLI не является

Проведено консилиумом флота и принято решением
`agent-fleet/decisions/2026-08-08-inbox-and-wakeup.md`. Граница сформулирована реализатором ядра
и принята всеми участниками:

> **«хранить и адресовать» — да; «наблюдать, решать, будить» — нет.**

Следствия, обязательные для реализации:

- **CLI не ведёт реестр живости.** Ни heartbeat, ни TTL, ни «жив ли исполнитель». Живость —
  отдельный компонент вне этого пакета (во флоте — ветка-лиз `fleet/lease-<линия>` с серверным
  CAS). Дописать реестр в store технически дёшево — и именно поэтому запрещено: ядро перестанет
  быть пассивным хранилищем и станет оркестратором;
- **CLI не решает, когда поднимать преемника.** Команда запуска (`go`) остаётся, но она —
  исполнитель чужого решения, а не место, где решение принимается;
- **CLI — оглавление эпизодической памяти, а не память.** В звено кладут указатели и факты,
  выводимые из git; durable-знание («грабли инфраструктуры», «решили так-то») живёт в
  `decisions/`, `runbooks/` и в памяти агента, а звено на него **ссылается**. Без явной границы
  в store начнут складывать всё подряд, и он перестанет быть индексом.

## 3. Инварианты, которые CLI обязан соблюдать

Все — из контракта; CLI ничего не изобретает, но обязан не нарушить:

1. **Отказать в записи нельзя.** Нет имени линии — присвоить техническое (`technicalUnit`), а не
   упасть. Сессия без handoff'а хуже, чем handoff с некрасивым именем.
2. **Ссылка на предка — по `id`, не по пути.** Переименование и переезд не рвут цепочку.
3. **Архивы v1 при миграции не двигаются.** У них нет `id`, единственная ссылка — абсолютный путь.
4. **`lineState` живёт в голове линии**, индекс — производный кэш. Пересборка индекса не
   воскрешает закрытые линии.
5. **Лок:** протухший определяется по pid **и времени старта процесса**, не по одному pid.
6. **Store — repo-scoped** (`git rev-parse --git-common-dir` с fallback), чтобы линии одного
   репозитория из разных worktree видели друг друга.

## 4. Команды

Все — **тонкие обёртки над существующими экспортами**. Новой логики не изобретать; если для
команды не хватает функции ядра, это повод остановиться и спросить, а не дописать.

| Команда | Что делает | Ядро |
|---|---|---|
| `store` | путь store, корень репозитория, признак fallback | `resolveStore` |
| `show [--unit U]` | текущее звено линии; без `--unit` — линия по умолчанию | `findHandoff`, `resolveDefaultUnit`, `readHandoff` |
| `write` | записать звено; вход — JSON на stdin | `writeLink` |
| `name <new> [--unit U]` | переименовать линию | `renameLine` |
| `fork [--from U]` | ветвить линию | `forkLine`, `deriveForkUnitName` |
| `parent [--unit U]` | разрешить ссылку на предка | `resolveParent` |
| `ancestors [--unit U]` | цепочка предков | `walkAncestors` |
| `graph` | граф линий | `renderGraph` |
| `doctor` | проверка store и документов | `doctorReport`, `validateStore`, `validateDocument` |
| `index rebuild` | пересобрать индекс из голов линий | `rebuildIndex` |
| `migrate` | перевести legacy-голову в v2 **без записи звена** | `migrateLegacyHead` |
| `incoming` | прочитать/снять указатель переезда | `readIncoming`, `relocateFromIncoming`, `removeIncoming` |
| `ask` | спросить сессию-предшественника через драйвер платформы | `querySession`, `src/drivers/*` |
| `go` | поднять преемника — **не тонкая обёртка**, см. ниже | `spawnBin`, драйверы, `markCommitted` |

**`ask` и `go` — платформенные.** Драйверы уже есть для `claude-code`, `pi`, `qwen`. Именно здесь
проходит граница «межагентное через общий формат, платформенное — в адаптере»: всё остальное в
CLI платформо-независимо, а эти две команды знают про конкретные бинарники и обязаны честно
падать с понятной ошибкой, если драйвера для платформы нет.

**`go` — единственное исключение из «тонкой обёртки», и это надо принять явно** (замечание
реализатора). `spawnBin` возвращает `ChildProcess` и больше ничего; за pi-командой
`/session-link-go` стоит: валидация spine, предупреждение о форке, keepalive, `markCommitted` и
старт с starter-prompt. Обёртка над одним `spawnBin` тихо потеряет всё перечисленное, а потеря
будет незаметной — преемник запустится, просто без половины гарантий.

**Решение: `go` в CLI обязан давать паритет с pi-командой**, и перечисленное входит в его
определение. Если паритет окажется дорог — уменьшать состав можно, но **только явно и списком**,
а не умолчанием.

**`migrate` почти всегда не нужна.** `writeLink` вызывает `migrateLegacyHead` сам при первой
записи, поэтому отдельная команда осмысленна ровно в одном случае: перевести legacy-голову, **не
записывая звена**. Так и описана; если этот случай никому не понадобится, команду убрать.

## 5. Общие правила

**Вывод.** По умолчанию — человекочитаемый. `--json` — машинный, и **только он стабилен**:

```json
{ "ok": true, "command": "show", "cliVersion": "2.0.0", "schemaVersion": "2",
  "data": { } }
```

При ошибке — `{"ok": false, "error": {"code": "not-found", "message": "…"}}`. Человекочитаемый
вывод менять можно свободно; `--json` — контракт, ломать только с мажорной версией.

**Общие флаги:** `--cwd <path>` (по умолчанию текущий каталог; store вычисляется от него),
`--json`, `--quiet`.

**`--store <path>` — не бесплатен, и это выяснилось при ревью.** Функции ядра принимают `cwd` и
зовут `resolveStore` сами; передать store напрямую сейчас нельзя — `writeLink(cwd, …)` пересчитает
его. Значит флаг требует либо варианта функций с явным store, либо подставного `cwd`. Пока это не
сделано, флага **нет**; вводить его вместе с реализацией CLI, а не считать данностью.

**Коды выхода** — семантические, чтобы скрипт не парсил текст:

| Код | Значение |
|---|---|
| `0` | успех |
| `1` | не найдено: нет линии, звена, предка |
| `2` | ошибка употребления: неверные аргументы |
| `3` | store занят: живой лок — **только у изменяющих команд**, см. ниже |
| `4` | документ не прошёл валидацию |
| `5` | конфликт: имя линии занято, звено уже существует |
| `6` | отказ по инварианту: попытка выйти за store, запись в чужой store |

**Чтение не блокируется записью.** `show`, `parent`, `ancestors`, `graph`, `doctor`, `store`
работают **при занятом store** — они не берут `withLock`, и код `3` к ним не относится. Под локом
и с кодом `3`: `write`, `name`, `fork`, `migrate`, `index rebuild`, `incoming` в режиме переезда.
Это свойство ядра, а не решение CLI, и ломать его нельзя: диспетчер обязан уметь читать состояние
линии в момент, когда линия пишет.

**Версионирование.** Версия CLI = версия пакета, и она движется **вместе со схемой**: мажорная
версия схемы `handoff.vN.json` = мажорная версия CLI. Обратное неверно — CLI может получить
мажорную версию из-за `--json`, не трогая схему. Обе версии присутствуют в каждом `--json`-ответе,
чтобы вызывающий не гадал.

## 6. Три вопроса — закрыты ревью реализатора

Все три были вынесены как «решить до реализации» и закрыты доводами по коду, а не голосованием.

**1. Линия в двух репозиториях — противоречия нет, формулировка уточнена.** `resolveStore` берёт
`git-common-dir` от **cwd работы**, а не запуска: `writeLink(cwd, …)` получает рабочий каталог.
Поля `cwd` и `sessionRef` в звене — артефакты (стартовая точка преемника, путь к транскрипту), а
**не ключи store**. Уточнение, которое надо держать в голове: «репозиторий работы» в смысле store
означает **`git-common-dir`**, общий для всех worktree одного клона, — то есть два worktree одного
репозитория дают **один** store, и это свойство сохраняется. Межрепозиторный индекс не нужен.

**2. `partOf` — изменение ядра, отдельным коммитом, и CLI его не вводит.** CLI не должен
заводить поля ядра: это ломает принцип тонкой обёртки. Порядок: сначала небольшое изменение ядра
(`partOf?: ParentRef`, второй тип ребра в `graph.ts`, строка в `toMarkdown`;
`resolveParent`/`walkAncestors` не трогаются), затем `show` и `graph` подхватывают его сами.
В этой спеке `partOf` — **отображается, если есть в звене**, и не является командой. «Сразу» —
значит в той же поставке, но коммитом по ядру, а не по CLI.

**3. `write` принимает JSON, вариант с флагами-фактами отклонён.** Довод реализатора решающий:
`writeLink` **уже** пересобирает `derived` через `collectDerived` при каждом вызове и сам
присваивает кодовую зону (`id`, `parent`, `seq`, `unit`) — то, что агент положит в эти поля,
перезаписывается. Значит «CLI собирает производное сам» дублирует работу ядра, не добавляя
безопасности. При этом авторская часть (`decisions`, `sections`, `blockers` — массивы и объекты)
через флаги передаётся плохо, и применимость сужается зря.

Допустимый guardrail: CLI предупреждает о полях кодовой зоны во входном JSON или молча их срезает.
Это косметика, а не смена модели, и на решение не влияет.

## 7. Приёмка

CLI считается готовым, когда:

- каждая команда из §4 имеет тест, гоняющийся тем же `node --test --experimental-strip-types`,
  что и существующие;
- `--json` каждой команды проверяется **против схемы**, а не «выглядит правильно»;
- коды выхода проверены отдельным тестом на каждый;
- **прогон на живой линии:** звено, записанное CLI из Claude Code, читается pi-адаптером, и
  наоборот. Это единственная проверка, ради которой всё затевалось, и без неё спека не закрыта;
- ни одна команда не создаёт файлов вне store и не пишет в чужой store — проверено тестом, а не
  чтением.

## 8. Чего я не проверял

- **Код ядра построчно не читал.** Поверхность снята по экспортам и размерам файлов; поведение
  функций взято из контракта и из имён. **Сверено ревью реализатора:** каждое имя из §4
  сопоставлено с реальным экспортом, инварианты §3 найдены в коде, объём ядра без `index.ts` —
  **2146 строк**. Приписанного ядру нет. Всё, что реализатор не мог подтвердить экспортами,
  вынесено в §4 и §5 как оговорки (`go`, `migrate`, `--store`, лок на чтении).
- **`ask`/`go` и драйверы** (`claude-code`, `pi`, `qwen`) не гонял ни разу; знаю только, что файлы
  существуют и экспортируют `querySession` и `spawnBin`.
- **Тесты не запускал** в этой ветке; знаю, что скрипт `test` указывает на `tests/**/*.test.ts`.
- **Тега `v2.0.0` ещё нет** — на `main` только `v0.1.0`, хотя PR #9 смержен. Версионирование в §5
  исходит из того, что тег появится.
