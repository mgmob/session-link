## 2. Зафиксированные решения

Архитектурные (из контракта):
- **store repo-scoped:** `<git-common-dir>/.pi/session_link`, fallback `<cwd>/.pi/session_link`.
- **ссылка по идентичности:** неизменный `id` + структурный `parent {id, unit, seq, store?}`; `parentHandoffPath` — подсказка (§2.5).
- **lenient-чтение:** `readHandoff` принимает `{v1,v2}`, проверяет минимум (семейство `schema`, обязательные поля, regex `unit`), **сохраняет незнакомые поля** при round-trip.
- **lock store-scoped** с признаком живости (pid + start) и перехватом протухшего.
- **`derived` собирается кодом; `checks` в MVP не собираются.**

Реализационные (в рамках контракта, подтверждены; если заказчик зафиксирует в контракте — обновить):
1. **Коллизия `id`** (совпадение ms + 4 hex при параллельной записи): `generateId` проверяет существование `handoff-<id>.json` в store и регенерирует hex до уникальности.
2. **Миграция v1→v2 (минимальная):** переносится **только голова** — получает `unit` (§3.2) и `id` (§2.5), конвертируется в v2 и ложится в `<store>/<unit>/`. **Архивы v1 остаются на старом месте** (у них нет `id`, перенос обнулил бы их `parentHandoffPath`-ссылки в потомках); разрешаются шагом 4 §2.5. Всю цепочку в v2 не переписываем; полная консолидация старых звеньев — отдельная операция обслуживания, не MVP.
3. **`parent`/`parentHandoffPath` при redo-in-place:** переносятся как есть (предок тот же); `derived` при этом пересобирается.
4. **Порядок инвариантов** в контракте исправлен (15–16 до 17); добавлен инвариант 23 (миграция не рвёт связь с v1-предками). Карта §4 здесь синхронизирована.

### Э2 — `readHandoff` {v1,v2} + `findHandoff` + линия по умолчанию → Э1
**Файлы:** `src/handoff.ts`, `src/store.ts`, `tests/read-find.test.ts`.
- `readHandoff(path)`: принимает семейство `{v1,v2}` по `schema`; v1 доносит поля как есть; **сохраняет незнакомые поля** (парсим в `Record` и работаем с объектом целиком, не проекцией в строгий тип). Для v1 без `unit`/`id` — нормализация на лету НЕ делается (чтение честное).
- `readIndex(store)` / запись `index.json` (позже в Э7 — здесь только чтение/отсутствие).
- `findHandoff(cwd, unit?)` (§2.3): 1) `<store>/<unit>/handoff.json`; 2) без `unit` → правило §4.3; 3) legacy `<cwd>/.pi/session_link/handoff.json`, **если рядом нет `MOVED-TO.txt`**; 4) ничего.
- Линия по умолчанию §4.3: одна `active` → она; несколько → чтение возвращает «перечень» (не путь), запись — отказ; ни одной → шаг 3. Реализовать как `resolveDefaultUnit(store): {unit} | {ambiguous: UnitSummary[]} | {none}`.
- `UnitSummary` (состав перечня §4.3): `unit`, `unitProvisional`, `state`, `seq`, `updatedAt`, `cwd`, первая строка `nextStep` головы; сортировка `updatedAt` убыв.
**Инварианты:** 7 (v1 читается), 18 (N>1 не выбирает за оператора).
**Готовность:** v1/v2 читаются; при 2 active `findHandoff` без unit даёт перечень.

### Э3 — `resolveParent` (§2.5) → Э2
**Файлы:** `src/store.ts` (или `src/parent.ts`), `tests/parent.test.ts`.
- `resolveParent(parent: ParentRef, store): {path} | {moved} | {notFound}` по 5 шагам §2.5:
  1. `<store>/<parent.unit>/handoff-<parent.id>.json` (одно обращение);
  2. `readdir` остальных `<unit>/` каталогов store на `handoff-<parent.id>.json` (после переименования);
  3. при `parent.store` — те же шаги в нём; если на пути `MOVED-TO.txt` — перейти и повторить;
  4. `parentHandoffPath` (v1-цепочки, последний шанс);
  5. ничего → честный отказ с `id` и последним известным путём.
- `walkAncestors(start, store)` — обход по `parent`/`parentHandoffPath`, стоп на первом звене без предка.
**Инварианты:** 4 (обход предков этой линии, incl cross-store), 20 (переименование не трогает архивы — разрешение через шаг 2), 21 (cross-store через `parent.store`+`MOVED-TO`), 22 (честный отказ).
**Готовность:** все 5 шагов покрыты тестами, включая перенесённый/переименованный/чужой-store предка.

### Э4 — Миграция v1→v2 (§2.4) → Э1, Э3
**Файлы:** `src/handoff.ts`, `src/store.ts`, `tests/migrate.test.ts`.
- При первой записи (детект: legacy-голова найдена по шагу 3 `findHandoff`, а пишем в `<store>/<unit>/`):
  1. legacy-голове присваивается `unit` (§3.2) и `id` (§2.5);
  2. **переносится только голова** (`handoff.json` + проекция `handoff.md`) из `<cwd>/.pi/session_link` в `<store>/<unit>/`, где конвертируется в обычное звено v2 и (при записи нового звена) архивируется как `handoff-<id>.json`;
  3. **архивы v1 остаются на старом месте** — у них нет `id`, и перенос обнулил бы абсолютные `parentHandoffPath` в потомках, порвав цепочку в точке миграции; разрешаются шагом 4 §2.5;
  4. в старом каталоге остаётся однострочный `MOVED-TO.txt` с абсолютным путём нового места;
  5. запись v2 идёт по новому пути; `parent` нового звена ссылается на мигрированную голову по `id`, а та — на v1-предка по `parentHandoffPath`.
- Столкновений не возникает (§2.4): каждая legacy-цепочка получает своё имя. Машинерия развилок (§6) **не** привлекается.
- v1-предки глубже головы остаются v1 (`parentHandoffPath`).
**Инварианты:** 7, 14 (legacy найден, перенесён однократно, маркер; повтор — не находит старую голову), 19 (две legacy из разных worktree → две разные линии), 23 (после переноса головы обход к v1-предкам возвращает те же звенья — архивы на месте).
**Готовность:** фикстура v1 после первой записи → v2 на новом месте, `MOVED-TO.txt` на старом, повторный поиск не падает.

- Содержимое `.lock`: `{pid, startedAt}` (время старта процесса — признак живости против reuse pid).
- Таймаут ожидания; перехват протухшего (владелец pid не жив или другой `startedAt`) с записью в лог; корректное освобождение в `finally`.
- Под локом — **все** пути записи: `writeHandoff` и `markCommitted` (read-modify-write живого файла после старта ребёнка).
- Внутри лока порядок §5: read index → случай §5.1 → fork-check §6 → архивация → write head temp+`rename` → write index temp+`rename` → release. **Данные первыми, индекс последним.**
- Проигравший гонку — внятный отказ (текст из §9).
**Инварианты:** 10 (параллельная запись не теряет данные, оба пути + протухший лок).
**Готовность:** две параллельные записи — одна отказала внятно, данные целы; kill процесса оставляет `.lock`, следующий запуск его перехватывает.

### Э6 — `writeHandoff`: три случая (§5.1) + `derived` → Э2, Э3, Э5
**Файлы:** `src/handoff.ts`, `src/store.ts` (`collectDerived`), `tests/write.test.ts`.
- Определение случая по голове линии и `sessionId`:
  - **redo-in-place** (голова есть, `sessionId` тот же): перезапись на месте, без архива, `parent`/`parentHandoffPath` сохраняются, `seq` **не растёт**, авторские поля `AGENT_BODY_FIELDS` переносятся вперёд (merge), `derived` **пересобирается**.
  - **новое звено** (голова есть, `sessionId` другой): голова → архив `handoff-<id>.json`, `parent` = `{id, unit, seq, store?}`, `seq` = `seq(головы)+1`.
  - **первое звено** (головы нет): `seq` = 1, `parent` отсутствует.
- `seq`-арифметика §7.2; производная линия при ветвлении от N → `N+1` (но сами развилки — Э8).
- `collectDerived(cwd, baseRef?)`: `branch` (`git rev-parse --abbrev-ref HEAD`), `commits` (`baseRef..HEAD`), `filesChanged` (`diff baseRef..HEAD` + рабочее дерево), `startedAt`/`endedAt`, `baseRef`. **`baseRef` обязателен для `commits`/`filesChanged`** — иначе пришлось бы угадывать базовую ревизию (тот же запрет, что для `checks`); нет `baseRef` → оба поля опускаются, не заполняются приблизительно. **`checks` не собираем** (MVP). Всё best-effort: git недоступен → поля опущены, запись не падает.
- `mergeAgentBody` адаптировать: при redo переносить авторские поля, но НЕ `derived` (он свежий).
- Обновить `toMarkdown` (проекция `handoff.md`, §7.1): имя линии + `seq`; **заметная пометка `unitProvisional` с подсказкой `/session-link-name`** (иначе провизорные имена не переименует никто никогда); блок фактов из `derived`. Проекцию читает оператор, решения — по ней.
**Инварианты:** 1 (unit переживает смену сессии/модели), 2 (две линии не смешиваются), 15 (умершая до авторства → `derived` заполнен, DRAFT), 16 (провал сессии не закрывает линию → `lineState` `active`), 17 (redo не плодит звенья, не стирает авторское).
**Готовность:** три случая покрыты; `summary` переживает пустую попытку авторства; `derived` у DRAFT.

**Файлы:** `src/handoff.ts`, `src/store.ts`, `tests/targetcwd.test.ts`.

### Э11 — `externals` (§8) → Э6
**Файлы:** `src/handoff.ts`, `tests/externals.test.ts`.
- `externals` — непрозрачный `Record<string, unknown>`; в json-schema неограничен.
- Потолок 32 КБ на блок: при превышении — отказ с ключом и размером (не обрезка).
- fail-soft: блок не сериализуется → handoff пишется без него + запись в лог.
- session-link **не пишет в `externals` сам** и не интерпретирует при чтении; round-trip произвольного JSON.
**Инварианты:** 6 (отсутствие/незнакомое `externals` не ломает), 9 (не пишет сам — сравнение до/после).
**Готовность:** 50 КБ блок → отказ; битый JSON-блок → handoff без него; чужие ключи переживают round-trip.

## 5. Риски и edge cases

- **`git-common-dir`:** bare-репо, submodule, symlinked `.git`, worktree с нестандартным расположением, git-бинарник недоступен → fallback. Smoke-тесты на каждый; при ошибке `git` — fallback, не падение.
- **Lock:** reuse pid на той же машине (отсюда `startedAt`), Windows `LockFileEx`/named-pipe нюансы, оставленный `.lock` после kill. Перехват протухшего — обязательная часть Э5, не откладывать.
- **`id` коллизия:** ms + 4 hex; регенерация (решение §2.1). На параллельных写入 под локом — маловероятно, но покрыть тестом.
- **Обратная совместимость:** инвариант 7 на **реальной** v1-цепочке владельца — **gate перед мержем**. Сгенерировать фикстуру в Э0 и прогонять на каждом этапе.
- **Windows:** cmd.exe, регистронезависимость FS (`Foo` vs `foo` — отсюда strict lowercase `unit`), пути с пробелами/кириллицей, `MOVED-TO.txt` кодировка.
- **Сериализация индекса:** детерминированная (фиксированный порядок ключей) для инварианта 3.
